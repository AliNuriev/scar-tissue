# INC-004 - Return dates shifted by one month for end-of-month bookings

**Date:** 2026-01-31
**Duration:** 5h
**Severity:** SEV-2
**Author:** Booking team

## Summary

Round-trip bookings made on 31 January with a one-month return produced return
segments dated 3 March instead of 28 February. Forty-one bookings were affected
before the flag was pulled.

## Timeline

- **08:00** - Normal traffic on the last day of the month.
- **14:20** - Customer calls about a return flight on the wrong date.
- **15:10** - Two more calls. Pattern recognised.
- **16:45** - Feature flag disabled for the "same date next month" shortcut.

## Impact

Forty-one incorrect bookings. Twenty-two required rebooking at our cost. The
remainder were caught before ticketing.

## What went wrong

The return date helper builds a new date by taking the departure date and
incrementing the month component directly, leaving the day component untouched.

For most dates this is correct. For 31 January it produces 31 February, which
the date constructor rolls forward into March. The same class of error exists
for 29, 30 and 31 of any month followed by a shorter one, and for 29 February
in a non-leap year.

The function was covered by tests. Every test case used a mid-month date.

## Resolution

Replaced the manual month arithmetic with the date library already present in
the project, which clamps to the last valid day of the target month.

## Action items

- Parameterised tests over month boundaries for every date helper.
- Ban raw date component arithmetic in favour of the shared helper.
