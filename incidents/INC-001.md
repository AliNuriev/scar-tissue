# INC-001 - Duplicate seat assignments on GX-455

**Date:** 2026-04-14
**Duration:** 3h 20m
**Severity:** SEV-2
**Author:** Platform on-call

## Summary

Nine passengers on flight GX-455 were issued boarding passes for seats that had already been assigned to someone else. The overlap was discovered at check-in, not by our monitoring.

## Timeline

- **09:12** - Seat map for GX-455 opens after the fare sale announcement.
- **09:12–09:19** — Traffic to the seat selection endpoint is roughly forty
  times normal.
- **11:40** - Gate agent reports two passengers holding 14C.
- **11:55** - On-call confirms nine duplicate assignments across six seats.
- **12:32** - Seat selection disabled for the flight.

## Impact

Nine passengers required manual reseating. Two were rebooked onto a later
flight. Support handled the reconciliation by hand against the booking table.

## What went wrong

`assignSeat` in the booking service reads the seat record, checks whether the
status is `available`, sets it to `booked` with the passenger id, and saves.
The read and the save are separate awaited calls.

Under normal traffic the gap between them is small enough that nothing collides.
During the sale, several requests for the same seat arrived inside that gap.
Each of them read the seat as available, each passed the check, and each wrote
its own booking. The last write won in the database; the earlier ones had
already returned success to the client.

We could not reproduce this locally. A single request always behaves correctly,
and the code had been reviewed twice without anyone noticing.

## Resolution

The check was moved into the write itself as a conditional update, so the
database decides which request wins and the losers receive an explicit failure.

## Action items

- Audit other endpoints that claim a limited resource: baggage allowance slots,
  upgrade vouchers, lounge passes.
- Add a load test that fires concurrent requests at the same seat.
