# INC-005 - Connection pool exhaustion after a partner outage

**Date:** 2026-02-19
**Duration:** 9h (slow degradation), 40m hard outage
**Severity:** SEV-1
**Author:** Platform on-call

## Summary

The fare aggregation service stopped serving traffic entirely after gradually
degrading over most of a day. A restart brought it back immediately.

## Timeline

- **06:00** - Upstream partner API begins returning 502s intermittently.
- **06:00–14:30** — Latency on fare search climbs slowly. No alert fires
  because no single request fails.
- **14:35** - Service stops accepting new work. Health check fails.
- **14:50** - Restarted. Service recovers instantly.
- **15:40** - Second restart needed. Investigation begins in earnest.

## Impact

Forty minutes of unavailable fare search during an afternoon peak. Revenue
impact estimated but not confirmed. The first restart was treated as a fix,
which cost us another hour.

## What went wrong

`fetchPartnerFares` acquires a connection from the pool, issues the request,
and releases the connection at the end of the function. When the partner
returned an error, the function threw before reaching the release call.

Each failed partner request therefore leaked one connection. With the partner
failing intermittently for eight hours, the pool drained slowly enough that
nothing looked wrong until it was empty.

Handle count was climbing steadily in metrics the whole time. Nobody was
watching that graph because it had never mattered before.

## Resolution

Moved the release into a `finally` block. Added a pool utilisation alert at 70%.

## Action items

- Audit every acquire in the codebase for a release on the failure path.
- Treat "fixed by a restart" as an unresolved incident, not a resolved one.
