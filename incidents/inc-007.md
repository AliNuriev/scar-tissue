# INC-007 - Negative price filter returning unpriced inventory

**Date:** 2026-04-29
**Duration:** 1h 15m
**Severity:** SEV-2
**Author:** Search team

## Summary

A crafted query string caused the fare search to return internal inventory rows
that should never be exposed, including seats held for staff travel.

## Timeline

- **21:14** - A user posts a screenshot of an unusually cheap fare on a forum.
- **21:40** - Reproduced internally with `maxPrice=-1`.
- **22:29** - Parameter clamped, deployed.

## Impact

No bookings were completed at the incorrect fares. The exposed rows contained
no personal data, but they revealed internal hold quantities.

## What went wrong

`maxPrice` and `minPrice` come off the query string and are passed into the
fare comparison without any check that they are numbers, that they are
positive, or that min is below max.

With a negative `maxPrice` the comparison inverted, and rows with a null fare
- internal holds that carry no price - passed the filter because a null
compares as less than a negative number in the query engine.

The parameter had been treated as a display concern rather than an input
boundary, so it was never validated anywhere on the path.

## Resolution

Both parameters are now parsed, bounded, and rejected with a 400 when they do
not form a valid range. Rows without a fare are excluded explicitly.

## Action items

- Treat every query string parameter as untrusted, including numeric ones.
- Add an explicit exclusion for unpriced inventory at the repository layer.
