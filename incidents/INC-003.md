# INC-003 - Search endpoint returning 500 on partner traffic

**Date:** 2026-03-08
**Duration:** 11h
**Severity:** SEV-3
**Author:** API team

## Summary

A partner integration began sending search requests that crashed the handler.
The error rate on `/api/search` sat at 4% for most of a day before anyone
connected the tickets to the deploy.

## Timeline

- **02:10** - Partner switches to a new client build.
- **02:15** - Error rate on `/api/search` rises from near zero to 4%.
- **11:30** - Partner emails asking why they are getting 500s.
- **13:05** - Root cause identified.

## Impact

Roughly 18,000 failed searches. The partner's own retry logic amplified the
load. No corrupted data, but the partner's confidence took a hit and we spent
the following week in review meetings.

## What went wrong

The handler destructures `passengers`, `origin`, `destination` and `departDate`
straight off the request body and passes them into the fare query. The new
partner build sends `passengers` as a string rather than a number, and omits it
entirely for one-way searches.

Nothing between the request and the query checks the type or the presence of
these fields. When `passengers` was missing the arithmetic in the fare
calculation produced `NaN`, which the query driver rejected, and the resulting
exception surfaced as a 500 rather than a 400.

The client was sending a malformed payload. We should have told them so in the
response. Instead we crashed and gave them no information to act on.

## Resolution

Added schema validation at the top of the handler. Invalid requests now return
400 with the offending field named.

## Action items

- Apply the same validation pattern to the remaining public endpoints.
- Alert on 5xx rate per endpoint, not just overall.
