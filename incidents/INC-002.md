# INC-002 - Booking history endpoint timing out for long-standing customers

**Date:** 2026-05-02
**Duration:** 6h (degraded)
**Severity:** SEV-3
**Author:** Backend team

## Summary

`GET /api/bookings/history` began returning gateway timeouts for a small group
of customers. The endpoint had been in production unchanged for two years.

## Timeline

- **07:40** - First support ticket: "my trips page never loads".
- **09:15** - Three more tickets, all from accounts created before 2022.
- **10:20** - Reproduced with a test account seeded with 4,000 bookings.
- **13:50** - Pagination added and deployed.

## Impact

Approximately 900 accounts affected, all of them frequent travellers. No data
loss. Support handled requests manually for the day.

## What went wrong

The handler fetches every booking belonging to the account, serialises the full
objects including nested passenger and segment records, and returns the array.
There is no limit, no page size, and no default cap.

This was fine in staging, where no seeded account has more than a few dozen
bookings. It was fine in production too, for two years, until enough customers
accumulated enough history. The endpoint got slower gradually rather than
breaking, so nothing alerted.

Memory on the API pods spiked during each of these requests, which was the
first signal anyone noticed in metrics, and even then it was read as noisy
neighbours rather than a query problem.

## Resolution

Added `limit` and `cursor` parameters with a default page size of 50, and
capped the maximum page size server-side.

## Action items

- Review every collection-returning endpoint for a missing limit.
- Seed staging with at least one account holding several thousand records.
